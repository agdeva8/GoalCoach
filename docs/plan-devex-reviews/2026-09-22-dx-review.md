## Persona (resolves open item #1)

The CEO doc's `§12 DX` names "outside-cohort first-time AI-coach user (not founder)." The product-design doc names the founder. These are not in conflict — they are two roles the layer-4 design serves:

- **Primary persona (v0): the founder.** Founder-as-first-user per layer-0 premise. Layer-4 onboarding flows (primer, chips, tooltips) are designed first against the founder's actual daily use. The founder uses the coach 5+ days/week; the primer is the daily-handhold.
- **Secondary persona (v1): the outside-cohort user.** 5 close friends joining at v1. Layer-4 onboarding flows must work for someone who has *never seen the product before* — the founder's own familiarity is a trap. The 5-primer-chip menu is the bridge from "I'm staring at a text box" to "I'm in a conversation." The 6 area chips teach the multi-horizon wedge without onboarding-tour interruption.

**Trade-off named and resolved:** layer-4 optimizes the *first 30 seconds of a session* for the outside-cohort user (cold start, primer is the entire affordance) and the *first 30 seconds of a return visit* for the founder (resume hint per L2 spec + primer). This is the only sensible split — the founder does not need primer chips; the friend does. Both render conditionally per L2 spec.

The persona card:

```
TARGET USERS (LAYER 4)
========================
Who #1:    Founder (frequent user, knows the wedge)
Context:   Daily use. Returning to a chat that should remember yesterday.
Tolerance: 5 seconds to "what should I do now?" — primer is a menu, not a tour.
Expects:   Resume hint + low-friction return.

Who #2:    Outside-cohort first-time user (cold start)
Context:   Arrived from a friend's text. Never seen the product.
Tolerance: 30 seconds to "this is real and I get it" — primer IS the onboarding.
Expects:   Primer chips that map to their actual life, not feature-tour language.
```

The layer-4 implementation tasks (T29–T35) serve both. Primer chips (T29) and brand line (L2) are for #2; resume hint (L2) and feedback loop (T35) are for #1; area chips (T30), card tooltips (T32), response-quality heuristic (T31), and offline banner (T34) serve both.

## Pass 1 — First Impression (Getting Started)

### Rating: 7/10 → 9/10 (after this review)

**What works (7/10):** Primer brand line + 5 clickable starter chips per the CEO doc's `§12 Pass 1`. Click fills input + sends. Replaces the empty text-box on first visit.

**Gap (the 2 missing points):** (a) The brand line voice is layered on top of L2 copy without explicit handoff. (b) The chip *content* didn't get reviewed at L4 — L2 specified 5 primer chips, but L4 should verify the chip set matches the persona's actual first-30-seconds mental model.

### Fixes

**Voice handoff from L2:** The brand line is L2 territory ("I'm your life coach. I help when you've got too much going on." — friendly, direct). L4 inherits it. **No conflict with L2 trust rules** (L2 forbids "Great job!" / "Welcome back!" / "Keep it up!" in coach voice; the brand line is the brand's voice, not the coach's. Different personae; different copy rules).

**Chip set review (T29):** The 5 chips from L2 are:
1. "Help me figure out this week."
2. "I just started a new goal."
3. "I'm juggling too many things."
4. "Walk me through my last conversation."
5. "Tell me what I'm over-committing to."

L4 review: chips #4 and #5 require ≥1 prior session. Per L2, they render as disabled-with-tooltip on truly fresh users (no session at all), and active on returning users whose `last_n_turns` is empty. **L4 confirms:** the chip-disabled state must surface the tooltip on tap (mobile) and on focus (keyboard) — aria-describedby per L2 a11y spec. Implementation file: `app/_components/PrimerPrompts.tsx`.

**Pre-flight review:** Before the primer renders, check (a) `user.sessionsCount > 0` and (b) `last_n_turns.isEmpty()`. If both are true, all 5 chips render. If only (b) is true, only chips #1–#3 render (active). If (a) is false, all 5 chips render (active) on a fresh cold start.

**Magical moment (per `/plan-devex-review` Step 0D adapted for end-user):** The first-30-seconds magic is *typing or tapping a chip and getting a response that names something the user didn't say*. Not "hi!" — a response that demonstrates the coach is reading. This is achieved by Pass 3 (response-quality heuristic), not by the primer. The primer's job is to get the user to send; Pass 3's job is to reward them for sending.

**Time-to-hello-world (TTHW) estimate for the outside-cohort user:**
- Land at URL → see brand line + 5 chips → tap chip #1 → 4–8s for first token (per L3 latency budget) → response names something the user didn't. **TTHW ≈ 8–12 seconds.** Competitive tier (2–5 min) is for SDK-style products; for a chat product, the relevant metric is "time to first response that surprises you," which is 8–12s. **Champion tier for this metric** would be < 5s; the L3 latency budget already requires it. The L4 design honors that budget.

## Pass 2 — Multi-horizon Affordance

### Rating: 7/10 → 9/10 (after this review)

**What works (7/10):** 6 hash-prefixed area chips below chat input (`#career  #health  #relationships  #finance  #learning  #fun`). Click fills input with `/area <name>` prefix.

**Gap (the 2 missing points):** (a) The 6 areas are listed without review of whether they're the right 6. (b) The interaction model (`/area <name>` as an in-band command) is unspecified at the UX level — is `/area` a typed slash command? Does the chip just type it? Does the coach parse it?

### Fixes

**Area set review (T30):** The 6 areas are career, health, relationships, finance, learning, fun. **L4 confirms:** these are the right 6 for a v0/v1 cohort product aimed at the founder + 5 outside-cohort users holding "more than one active goal across horizons." They cover the canonical life domains without being prescriptive. Implementation file: `app/_components/ChatInput.tsx`.

**Interaction model (T30):** Clicking an area chip DOES NOT type a slash command. Slash commands add cognitive overhead and a parsing layer. Instead, clicking an area chip:
1. Fills the input with the user's own drafting — e.g., `#career` chip fills input with "I'm thinking about career:" + cursor. The user finishes the sentence.
2. The hashtag is treated as a *display hint*, not a parsed command. The AI's `update_areas` tool (per L3) takes the user's stated goals and infers area from context. The hashtag is purely a wayfinding cue.

This is simpler than `/area <name>` and removes a parsing surface (no `/area` command implementation needed in L3).

**Visibility rules (T30):** Area chips render only on cold-start OR when the chat is "between conversations" (no `last_n_turns` AND user has fewer than 3 prior turns). After 3 turns, the chips hide — they've done their teaching job. They can be re-shown by clicking a "↻" button next to the input. This matches L2's pattern of "subtle, visible, teaches without shouting."

## Pass 3 — Response Quality Floor

### Rating: 7/10 → 8/10 (after this review)

**What works (7/10):** System prompt enforces heuristic: AI response must reference specific words/phrases from user input (rubric B = "names pattern/tension user did not name"). If response doesn't pass: show inline "let me try again" button. Same retry budget as malformed tool calls (2 retries/turn; on exhaustion text-only fallback per T6 / L3 D13).

**Gap (the 1 missing point):** The rubric is evaluated at build time, not at runtime. The L4 UX claim is "the coach will always name what you didn't say" — but the only enforcement is system-prompt instruction + build-time rubric. There's no per-response runtime check.

### Fixes

**Heuristic at runtime (T31):** Implementation: after the AI responds, the route handler (L3) calls a tiny classifier on the response (deterministic, no LLM call): does the response contain at least one noun or named entity that appears in the user's message OR is clearly grounded in the user's named goals/areas? If yes, ship the response. If no, trigger the retry button + send a corrected prompt back to the AI (counts against the 2-retry/turn budget per L3 D13). This is a *runtime* check, not build-time.

The classifier is intentionally simple: substring overlap with user message + keyword overlap with the user's goals table. It catches "AI says something generic" without needing an LLM-as-judge (which would double latency).

**Retry button UX (T31):** When heuristic fails: the response renders anyway (we don't want to lose it), but a small "↻ Try again" button appears below it. Click = AI re-runs with the original prompt + a "your previous response didn't reference what the user said; try again" instruction. **2 retries max per turn.** On exhaustion, the response ships as-is and the button hides.

**Honest gap:** the heuristic does not enforce the rubric *quality* (does the response name a *pattern* the user didn't, not just *any word overlap*). That requires the L0 rubric at build time, not at runtime. The runtime heuristic is a floor, not a ceiling.

## Pass 6 — Offline / Network UX

### Rating: 6/10 → 8/10 (after this review)

**What works (6/10):** Detect offline via `navigator.onLine`. Banner: "You're offline — your message will send when you reconnect." Queue last message in `localStorage`. On reconnect: send queued. Refresh mid-turn: client resumes stream via event-id.

**Gap (the 2 missing points):** (a) Cold refresh mid-stream — does the event-id resume actually work? The CEO doc says "specced; full impl P2." (b) What happens to *already-sent* AI responses when offline mid-stream?

### Fixes

**Refresh-resilient streams (T34):** The event-id resume is specced (the route handler emits an `event_id` with each chunk; client tracks last `event_id`; on reconnect, client sends `?resume=<event_id>` and the stream continues from there). **L4 review:** full impl is P2. **Verdict:** v1 ships with the spec, AND the implementation. Why: if a user refreshes mid-stream and loses everything, the failure is loud and embarrassing (the founder is user #1, will hit this within a week). Better to ship the full impl than to defer.

Implementation:
- Client: tracks `event_id` in `localStorage` per active conversation.
- On page load with `localStorage.event_id` set: send `?resume=<event_id>` to `/api/chat/stream`. If server has the chunk in its write-ahead log (TTL: 5 minutes), it resumes. Otherwise returns 410 → client renders a clean "stream expired" message + chat continues normally.
- Server: write-ahead log keyed by `event_id` with 5-minute TTL. `lib/chat/event-log.ts` (new). Implementation file: `app/api/chat/stream/route.ts`.

**Already-sent AI responses on offline:** if the user is reading a streamed response and goes offline mid-stream, the partial response is preserved in local state (React state). On reconnect, the stream resumes from the last `event_id`. No re-prompt, no double-charge.

**Offline banner UX (T34):** Banner top-of-chat, `<aside role="status" aria-live="polite">`. Text: "You're offline. Your message will send when you reconnect." Disappears on `online` event. Does not auto-retry the user — they must press Send again to flush the queue (avoid surprise sends). Implementation file: `app/_components/OfflineBanner.tsx` (new), `lib/offline/queue.ts` (new).

**Edge case:** if the user types while offline, the input is disabled with a tooltip "You're offline — type will be saved locally and sent on reconnect." This avoids a silent loss where the user types a long message, it sits in the queue, and on reconnect it sends but the user has navigated away.

## Pass 8 — Feedback UX

### Rating: 6/10 → 7/10 (after this review; closing-the-loop deferred)

**What works (6/10):** Each AI message has tiny thumbs-up + thumbs-down icons below (lucide). Click opens one-line optional comment field. Data stored in new `feedback` table (user_id, message_id, rating, comment, ts). No v1 action; feeds v1.1 ranking + persona-aware thinking improvements.

**Gap (the 1 missing point):** The feedback loop is one-way (user → DB) with no closing-the-loop. A user who thumbs-down a response gets nothing back. That's the gap between "data exists" and "the user feels heard."

### Fixes

**Closing-the-loop (deferred to v1.1, honestly):** v1.1 spec: when a user thumbs-down a response, after 24h, the next coach response explicitly acknowledges ("Last time I missed something — let me try again from where you were.") This requires the v1.1 persona-aware thinking layer to be built first. **v1 does not ship closing-the-loop.** The thumbs UI exists; the data flows; the user knows the data flows (a small "Thanks — we'll do better" toast on submit). That's the honest v1 UX.

**Feedback toast (T35):** On thumb-click (with or without comment): toast at the bottom of the screen, "Thanks — this helps." 3-second fade. This is the *minimal* closing-the-loop — no promise of follow-up, just acknowledgment. The user feels heard without us over-promising.

**Schema for feedback (T35):** `feedback` table — owned by L3 (migration). L4 owns the UX. Schema:
```sql
CREATE TABLE feedback (
  id            BIGSERIAL PRIMARY KEY,
  user_id       UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  message_id    BIGINT NOT NULL REFERENCES messages(id) ON DELETE CASCADE,
  rating        SMALLINT NOT NULL CHECK (rating IN (-1, 1)),
  comment       TEXT,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX feedback_user_created ON feedback (user_id, created_at DESC);
```
This is L3 territory; L4 inherits the contract. (Resolves open item #4: closing-the-loop is not in v1; thumbs + storage + acknowledge-toast are.)
